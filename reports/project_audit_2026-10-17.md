# 当前项目实现审计｜2026-10-17

## 范围与判断边界

本报告用于将本项目与移动应用开发竞赛作品进行比较。依据为 2026-10-17 工作区当前文件、只读 SQLite 查询，以及隔离执行现有纯函数的确定性检查。本轮只新增此报告，未修改产品代码、模型、数据库。原工作区已有 `backend/serve.py`、`frontend/app.js`、`frontend/index.html`、`frontend/style.css` 未提交修改。

**已实现**表示代码中存在相应逻辑；**本轮实测**只包括下文列出的只读数据库查询与使用模拟分类器的纯函数检查。没有启动实际模型、浏览器、手机或完整 HTTP 服务，因此不能把代码存在写成端到端通过。

关键提醒：根目录 README 已落后于当前代码。README 第 7、67 行仍描述单条说明、三类分数及示例；当前页面已经转为 PDF/DOCX 上传、整篇审阅、流式逐句进度、仅展示疑似矛盾。比较时应以当前代码为准。

## 结论

现阶段并非只有“输入一句话、调用一个模型”。已经形成了“文稿提取—清洗分句—限定资料检索—逐句推理—显示原文与出处”的审阅原型，而且有本地证据治理、训练与诊断工作。

不足主要在三个层面：

1. **结果可信度尚未形成可验证的承诺**：信息不足会显示为“通过”；领域标签待人工复核；原句复制诊断仍出现误判；整篇审阅缺少独立端到端评测。
2. **审阅任务没有完成闭环**：目前停留在指出疑似矛盾，缺少确认/驳回、修改、复核、导出、记录版本等后续动作。
3. **移动场景和交付证据薄弱**：有响应式页面，但没有在仓库中看到移动应用工程、PWA 配置、小程序工程或可安装包；默认服务仅监听本机，未验证手机使用。

上述短板比增加商城、社区、聊天机器人、3D 展示等无关模块更直接影响这个项目的完整性。

## 本轮确证数据与行为

### 数据库只读查询

连接 `file:data/costume.db?mode=ro` 查询结果：

- sources：50 份。
- evidence_chunks：approved 99、pending 142、rejected 414，共 655 条。
- approved 证据覆盖：43 份来源。
- verifications：0 条。
- verification_items：0 条。

数量与 `reports/evidence_review_2026-10-14.md:16` 一致。其第 3 行也明确本轮大批审核由助手阅读原文完成，未替代专家对历史文化和工艺术语的复核。竞赛材料不能把 99 条全部表述为“专家审核金标准”。

### 信息不足与“通过”的混同：已用模拟分类器复现

方法：从 `backend/serve.py` 的 AST 提取现有检索、相关性、审阅函数和所需常量，在隔离命名空间执行；实际数据库只读；模拟分类器返回固定标签，不载入权重、不测模型质量。输入“这件棉袍采用对襟设计。”，默认 source_id=1。

| 模拟模型标签 | 实际调用次数 | 返回 problems | 推送状态 |
| --- | ---: | ---: | --- |
| supports | 1 | 0 | pass |
| insufficient | 1 | 0 | pass |

根因：`backend/serve.py:249` 跳过所有非 refutes 的预测；`:273` 在没有选出反驳证据时统一 report pass。`frontend/app.js:251` 把 pass 翻译为“通过”。当前页面最终“未发现矛盾”本身不是“证实正确”，但逐句绿色“通过”的含义更强，容易误导。

建议优先保留并明确区分：有支持证据、疑似矛盾、信息不足、未找到相关资料、技术原因未检查。未查到矛盾不能替代已支持。实际状态合并规则应在对照标注集上验证。

### 多对象文稿的上下文断裂：检索层已复现

默认资料选棉袍（source_id=1），先后输入：

1. “新疆喀什维吾尔族花帽采用手工平绣装饰。”：跨资料检索 found，候选 source_id=2；内容重合分为 5、1。
2. “帽里衬以黑色棉布。”：跨资料检索 needs_context，退回默认 source_id=1；候选全部来自棉袍，内容重合分为 1、1、0、0，低于 MIN_RELEVANCE=2。

这说明当前不会承接上一句已识别出的“花帽”对象。`backend/serve.py:196` 每句独立做全库检索，`:198` 失败后回到同一个手选来源；没有段落/标题/对象状态。`:159` 还先滤掉标题，未把标题中的对象信息保留为后文上下文。

合理改进不是简单扩大 Top-K，而是保留章节、段落、对象映射与可见的用户确认；让“它/这顶帽子/帽里”等句子承接正确对象；遇到多对象歧义时请求确认或标记未确定。这个环节会直接决定整篇审阅的召回率。

## 主要产品缺口与优先级

### P0：先让审阅结论与验证范围一致

- **状态语义**：修复 insufficient→pass；展示未检查/未知覆盖范围，避免“0 处矛盾”被当作“全文正确”。依据：`backend/serve.py:249`、`:273`；`frontend/app.js:251`、`:435`。
- **模型可靠性**：现有领域测试标签是 AI 初拟待人工复核（实验日志第 10 行），并非可引用的正式领域评测；20 条原句复制仅 10 条支持（第 18 行），且有原句判反驳（第 25 行）。优先做输入/标签顺序/批次一致性排查和人工复核的冻结测试集。
- **端到端质量**：除三分类 F1，还应测证据召回、对象归属、错误句召回/精确率、未覆盖比例、每篇耗时。文字测试集应按来源或对象划分，避免同一原文派生样本落入训练和测试两边。这里是建议设计，尚未实现。
- **长句与部分失败**：模型输入各限 160 token（`backend/inference.py:19`、`:85`）；`review_document` 内部推理没有逐句异常隔离，外层流处理捕获异常后整篇 error（`backend/serve.py:562`）。应能把某句标记“未检查/过长”，保留已完成结果，支持拆句或重试。

### P1：完成一个编辑者能交付结果的任务

当前输出是“问题句+证据原文+出处”，没有形成后续审阅动作：

- 原文定位：后端返回 sentence_start/end（`backend/serve.py:257`），前端结果未使用；原稿是 readonly textarea（`frontend/index.html:100`），不能点击问题回到相应原文，也不保留原 PDF 页码或 DOCX 段落信息。
- 人工复核：没有确认问题、误报驳回、备注、依据选择、复核者记录。
- 修改与二次核验：没有修改稿、修改前后差异、重新核验和已解决/未解决状态。
- 导出与分享：当前前端没有报告下载、审阅标注导出或可追溯分享；应先实现一份清楚的审阅报告，含原句、证据、出处、人工决定、未覆盖范围、模型/资料版本和时间。
- 历史：数据库 schema 已有 verifications/verification_items（`backend/init_db.py:43` 起），但服务以 mode=ro 打开（`backend/serve.py:291`），本轮查询两表均 0，不能把建表等同于历史功能已完成。

无需先上复杂协作平台。一个“上传—定位—核对—人工确认—修改—再核验—导出”的完整小场景，已经比加多个脱离主线的入口更有价值。

### P1：明确真正的移动应用场景与交付方式

- 目前是响应式浏览器页面，实际默认服务在 `127.0.0.1:5173`（`backend/serve.py:672`），不能仅因 CSS 能缩成手机宽度就声称已经完成移动端交付。
- 本轮文件清单未见 Android/iOS 项目、微信小程序配置、PWA manifest/service worker 或安装包。仓库之外是否已有部署或安装成果未查证。
- 上传 PDF/DOCX 的场景更接近编辑审稿。若选择移动赛道，要明确手机端用户为什么在现场使用：例如讲解员现场核对展签、学生实地调研核对讲解稿；从文件选取、拍摄/OCR、网络等待、拇指操作、现场展示出处等环节决定最小移动形态。
- 原生 App、小程序、PWA 哪种符合本届规则，需另行核对官方赛项要求，不能仅由仓库推断。此审计不判定参赛资格。
- 先做真机贯通一个场景，记录实际机型、网络、耗时、失败恢复，再决定是否加入 OCR；当前 OCR 明确未实现（`backend/document_upload.py:91`、`:130`）。

### P2：让资料治理与创新点看得见

- 99 条 approved 是较小的有界语料，不宜先宣传“传统服饰通用核验”。可以明确从维吾尔族服饰的一组馆藏/工艺资料切入，并展示覆盖对象、属性、来源层级与局限。
- 现在资料审核依赖命令行脚本。若有管理角色真实需求，可把证据浏览、出处定位、待审队列、专家复核纳入管理端；不要为了增加页面数量做空后台。
- 界面目前看不到原文字符定位、资料审核状态/版本、模型版本、分类分数或不确定性解释。展示应服务于人的复核，避免将 softmax 分数直接宣传为事实真概率。
- 记录与当前产品同步：README、backend README 和 tests README 都应更新到整篇审阅实现，方便评委复现。

## 测试与交付材料缺口

仓库现有 `tests/test_bert_encoder.py`，`tests/README.md:5` 记载 9 项编码器测试；`:7` 明确范围仅编码器。本轮文件清单未发现文档提取、分句、路由、检索、审阅状态、流协议、前端或移动端的自动化测试。

当前可展示技术工作已不少；应补的材料是“真实任务如何完成、错误如何处理、效果如何验证”：

1. 目标用户与一份真实文稿的审阅流程、现有人工步骤和痛点。
2. 人工复核的独立测试集与固定评测报告，明确未覆盖范围。
3. 对照方案：纯关键词/规则、普通文本推理模型、当前模型与检索策略，在同一数据上的结果；不要只展示自研模型单个指标。
4. 至少若干真实用户任务观察，记录完成时间、误报复核时间、问题发现率与可理解性；样本数应诚实披露。
5. 真机演示录屏、故障恢复、最终审阅报告与修订前后样例。

**建议优先顺序：状态正确与领域验证 → 多对象上下文 → 原文定位和人工复核/导出闭环 → 真机移动交付 → 资料管理与进一步扩展。**
